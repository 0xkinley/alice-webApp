# Bounded Untrusted File Retrieval and PDF Suggestions

Status: Implemented locally for modern Office uploads, clean UTF-8 text/Markdown/CSV/TSV/JSON reads, PDF embedded text, host attachment save offers, capability-gated transfer, and pre-targeted upload fallback in Milestone 06

Decision date: 2026-08-31; format expansion: 2026-09-06

## Reference boundary

Consumption contract `2.4` may advertise current clean file references in one exact name-resolved, permission-filtered project package. It never embeds file bytes. The server preserves internal scope checks while omitting opaque project identity, internal context identity, and scope from the model-visible package. Selection excludes removed references, every superseded logical-file version, non-clean objects, and records the user cannot currently access. Returned metadata is bounded to the immutable reference, logical file/version, display name, verified media type, byte size, SHA-256, source host, and reference time. Model-visible text repeats the name, type, size, source, exact file-reference identifier, and supported read path for text-only hosts. Storage keys, object version identifiers, credentials, signed URLs, and scanner tags remain server-side.

File references are always labelled `reference_only_untrusted`. Clean `text/plain`, `text/markdown`, `text/csv`, `text/tab-separated-values`, and `application/json` references advertise `read_project_file_text`; clean PDFs advertise `read_project_file_pdf_text`. Each capability field is nullable and is populated only when the MCP process has the shared private-file adapter configured. Images and modern Office files remain metadata-only through MCP. DOCX, XLSX, and PPTX are explicitly reference/download-only; alice. does not claim that their contents are readable.

## Exact structured-text reads

`read_project_file_text` reauthorizes the exact project, active membership, required internal read capability, and current ChatGPT or Claude connection. It re-resolves the current clean logical-file version and append-only removal state. Foreign, guessed, superseded, removed, non-clean, inaccessible, and versionless references return the same unavailable response.

The object store is called with the immutable internal key and exact object version. Before fatal UTF-8 decoding, alice. requires both the downloaded byte size and SHA-256 to match PostgreSQL metadata. Plain text, Markdown, CSV, TSV, and JSON are treated as opaque text; alice. does not execute formulas, follow links, evaluate JSON values, or infer a schema. The caller supplies a 2,000–32,000 UTF-8 byte budget, defaulting to 8,000, and an optional zero-based Unicode code-point offset. alice. returns the largest exact excerpt whose complete serialized JSON response fits that budget. Concatenating successful continuation pages reconstructs the exact decoded source.

## Deterministic bounded PDF extraction

`read_project_file_pdf_text` applies the same authorization, current-version, clean-scan, exact-object-version, byte-size, SHA-256, complete-response budget, and Unicode continuation rules. It uses the pinned `pdfjs-dist@6.2.108` parser and extraction contract `pdfjs_embedded_text_v1`. Extraction is serial and deterministic: page text items are joined with fixed whitespace normalization, pages are separated by two newlines, and offsets address that canonical Unicode code-point sequence.

The operation accepts at most 200 pages, 50,000 text items per page, 250,000 text items overall, and 2,097,152 canonical Unicode code points. The output reports parser/method, total/text/textless page counts, intersecting page numbers, exact excerpt SHA-256, continuation, complete JSON byte use, and omissions. Encrypted, malformed, over-limit, and unsupported PDFs fail explicitly. PDF links and embedded instructions are not followed, no rendering is exposed through MCP, and no OCR, image understanding, attachment transfer, embeddings, or model orchestration occurs. An image-only PDF therefore produces no inferred text.

These counters limit accepted work but do not provide a separate parser-process memory sandbox. Live private-alpha deployment must retain upload limits, malware scanning, runtime resource limits, dependency updates, and operational monitoring; the local parser checkpoint is not a claim that arbitrary hostile PDFs are risk-free.

## File-to-candidate suggestions

`suggest_project_updates_from_file` is registered only with private-file capability and requires `mcp:write`. Its description limits use to an explicit user request to suggest or save project information from a PDF. The host supplies one exact project, candidate claims, and an extraction receipt containing only the fixed extraction version, start/end Unicode offsets, and excerpt SHA-256. It cannot supply a different source excerpt, file provenance, internal destination, acceptance status, or trusted state.

alice. reauthorizes the exact project and current clean PDF with write capability, fetches and integrity-checks the same immutable object version, reruns the deterministic extraction, and requires the receipt hash and range to match. The source range is limited to 12,000 code points. The server resolves the internal destination and rejects a changed, superseded, removed, guessed, foreign, or inaccessible source before capture.

The server—not the host—constructs the exact evidence payload. It includes the exact excerpt and bounded provenance: reference/logical-file/version, content SHA-256, display name, source context, parser/extraction version and method, range, excerpt SHA-256, and page count. Migration `014_pdf_evidence_sources.sql` adds a one-to-one immutable relational link from the evidence event to that exact file object/reference and extraction receipt. Composite foreign keys, exact metadata checks, current-version checks, immutable triggers, and constrained-role denial prevent provenance from being detached, rewritten, or deleted.

The existing atomic capture path stores the evidence, relational file source, pending candidates, context targets, and one content-free audit receipt together. Idempotent retries can only return the complete original receipt. The tool never inserts accepted state. The alice.-controlled exact review preview labels the PDF and excerpt untrusted, shows immutable hashes/version/range, and requires the authenticated human check action before every candidate becomes active; the cross action activates nothing.

## Trust and mutation rules

All retrieved or extracted content is `untrusted_artifact` data. Malware-clean, successfully parsed, host-generated, or user-uploaded does not mean alice.-verified. Content cannot become an instruction source, expand access, select another file or context, trigger tools, or activate its own statements. Ordinary file reads create no evidence, candidates, accepted state, file lifecycle changes, or project/audit mutations. A file-suggestion call is a separately authorized explicit capture and creates pending evidence-backed candidates only.

## Modern Office upload boundary

Migration `019_popular_file_formats.sql` expands upload, host-offer, immutable-object, and context-package media-type constraints to DOCX, XLSX, and PPTX, plus CSV, TSV, and JSON. Modern Office files retain the 25 MiB file limit; structured-text files retain the 2 MiB limit. Browser upload and replacement inputs expose the same explicit allowlist.

DOCX, XLSX, and PPTX are accepted only when the bytes are a bounded single-disk, non-Zip64 ZIP package with a valid central directory, `[Content_Types].xml`, exactly one matching primary Office part, and no `vbaProject.bin` entry. A renamed generic ZIP, mismatched Office extension, ambiguous package, encrypted entry, unsupported compression, malformed path, or macro-enabled package fails before immutable storage. This package inspection does not make document content trusted or safe; the existing malware scan remains mandatory.

Office files are scan-gated references with authorized download and metadata-only preview in this alpha. alice. does not yet extract DOCX paragraphs, XLSX cells or formulas, or PPTX slide text. Legacy binary `.doc`, `.xls`, and `.ppt`, arbitrary `.zip`, cloud-native Google Docs links, and non-PDF binary extraction remain unsupported. A Google document must first be exported to a supported file type; a future Google Drive integration would be a separate permission and provenance boundary.

## Metadata-only host attachment save offer

`offer_host_file_save` is available only with the private-file adapter, a ChatGPT- or Claude-classified connection, `mcp:write`, and one exact writable name-resolved project; the project may be omitted only for a sole writable project. Every new chat attachment offer stores the server-resolved internal destination. It creates no file object and accepts no attachment bytes or reusable host location. Its strict input is limited to the project reference, a safe filename, optional host-declared type/size/hash, an optional opaque conversation identifier, and an idempotency key. Prompt/message text, cookies, credentials, attachment URLs, internal destination overrides, and confirmation fields are unknown and rejected.

Migration `017_host_file_save_offers.sql` stores one immutable offer bound to the connection and exact project. Migration `021_single_action_save_previews.sql` makes undecided offers and their random app-authority digests short-lived preview state. The alice. MCP App or authenticated web fallback reauthorizes the same signed-in user and current destination write access, verifies the exact preview, and permits one decision: Save. New offers have no Cancel or suggestion branch and never enter Needs attention. Before Save there is no audit, transfer authority, byte, file reference, candidate, or accepted-state write. Closing, ignoring, or expiry is no action, and expired undecided previews are purged. Save grants no host credential and receives no bytes, so it cannot truthfully return a saved-file receipt.

## Confirmed host attachment transfer and fallback

Migration `018_host_file_transfers.sql` links each later attempt to the exact Save decision and existing direct-upload intent. A host may call `begin_host_file_transfer` only when its exact surface can securely expose the original attachment and perform `exact_signed_put_v1`; the strict call carries only offer ID, exact filename/type/size/SHA-256, capability literal, and idempotency key. The server derives the connection, uploader, source host, destination, access, and optional opaque conversation reference from the offer. No host credential, attachment URL, byte payload, prompt, message, or conversation text is accepted or stored. The returned presigned PUT is a ten-minute, exact-key/size/type/hash capability and is not persisted in PostgreSQL or logs.

When the provider surface cannot satisfy that contract, the already-authenticated offer URL renders one alice.-controlled file input. Project, source host, and decision are visible but not editable; internal routing is hidden. The browser requires the local filename to equal the confirmed name, hashes the file locally, and uses an exact-origin JSON route to create the same immutable direct-upload intent. No project or internal context identifier is accepted from the form. Both paths reauthorize current destination write access; a transfer not yet started also requires the offer to remain within its 30-minute window.

`finalize_host_file_transfer` and the browser finalizer accept only the exact linked intent, transfer path, initiating principal, and S3 version. The ordinary project direct-upload finalizer rejects host-linked intents. Staging bytes are neither read nor referenced before GuardDuty reports clean. After a clean staging result, alice. independently validates signature, normalized type, byte size, and SHA-256, stores the exact bytes through the normal immutable object/reference flow, and preserves source host, authenticated uploader, reference time, and content hash. The bounded conversation identifier stays on the offer and remains reachable through the relational transfer receipt without copying conversation content.

The newly stored reference remains unavailable while its final exact object version scans. Finalization returns only a pending stage until that result is clean; only then does one immutable availability row and one content-free audit event support a saved-file receipt. An offer-scoped advisory lock at `READ COMMITTED`, exact composite foreign keys, and unique completion/availability rows make different simultaneous upload attempts converge on one reference. No action, expired or stale unstarted authority, lost access, foreign/guessed IDs, metadata mismatch, non-clean scan, generic-finalizer bypass, and wrong-path replay fail closed.

New chat attachment saves always produce `suggestions_requested: false`. They do not create evidence, candidates, accepted state, automatic extraction, or a Needs attention item. A later explicit PDF suggestion must independently satisfy the extraction receipt and authenticated review boundary documented above. Historical receipts may retain the earlier `save_and_suggest_context` and `cancelled` decision values, but neither is offered or accepted for new decisions. Native capability is still `Not tested` for every provider surface until a dated live matrix run proves it; the browser fallback is the implemented safe path, not evidence of native provider support.
